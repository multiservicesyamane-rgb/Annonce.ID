# PRD COMPLET — WANTEERMAKO

## Évolution Marketplace → Marketplace + Services + Gestion d'activité

**Version : 1.0**
**Statut : Document de cadrage produit**
**Plateforme : Wanteermako.com**
**Cible : Web responsive / Mobile-first**
**Public cible : Acheteurs, vendeurs, prestataires, freelances, artisans, petites entreprises et agences en Afrique de l'Ouest**

---

# 1. VISION PRODUIT

Wanteermako est aujourd'hui une marketplace permettant aux utilisateurs de :

* découvrir des produits ;
* publier des annonces ;
* créer une boutique ;
* vendre directement ;
* contacter les vendeurs ;
* utiliser WhatsApp, appel ou messagerie ;
* recevoir des avis ;
* booster leurs annonces ;
* acheter des crédits et services de visibilité.

La prochaine évolution consiste à ajouter une **couche professionnelle de gestion d'activité**, sans transformer Wanteermako en un ERP complexe et sans casser l'expérience marketplace existante.

## Vision cible

> **Wanteermako permet de découvrir, vendre et gérer son activité depuis un seul espace.**

Le parcours complet devient :

**Découvrir → Contacter → Convertir → Réaliser → Facturer → Être payé → Fidéliser**

Pour un vendeur de produit :

**Annonce → Contact → Vente → Avis**

Pour un prestataire :

**Service → Prospect → Devis → Projet → Facture → Paiement → Avis**

---

# 2. PRINCIPES PRODUIT NON NÉGOCIABLES

## 2.1 Ne pas créer un deuxième Wanteermako

Il ne faut PAS créer :

* un dashboard Freelance séparé ;
* une application Services séparée ;
* un CRM séparé ;
* un compte professionnel séparé.

Toutes les fonctionnalités doivent fonctionner dans le compte Wanteermako existant.

---

## 2.2 L'utilisateur ne doit pas voir toutes les fonctionnalités

Wanteermako doit utiliser une logique de **progressive disclosure**.

Un utilisateur qui utilise uniquement la marketplace ne doit pas être confronté à :

* CRM ;
* projets ;
* devis ;
* factures ;
* documents ;
* ressources.

Ces fonctionnalités apparaissent lorsqu'elles deviennent pertinentes.

---

## 2.3 Le contexte prime sur le menu

Une fonctionnalité ne devient pas automatiquement un élément du menu principal simplement parce qu'elle existe.

Exemple :

Un contrat doit être accessible depuis un projet ou un devis.

Un formulaire doit être relié aux prospects.

Une facture doit être liée à un client/projet.

Un document doit être accessible depuis son contexte.

---

## 2.4 Mobile-first

L'expérience doit être conçue d'abord pour :

* smartphone ;
* connexion parfois limitée ;
* utilisation sur le terrain ;
* WhatsApp ;
* actions rapides.

Desktop = espace de productivité.

Mobile = espace d'action rapide.

# 55. SÉCURITÉ

# 80. CONCLUSION PRODUIT

Le nouveau module ne doit pas être présenté comme :

**"Wanteermako ajoute un CRM, un outil de gestion de projet et un logiciel de facturation."**

La bonne vision est :

> **Wanteermako évolue d'une marketplace de mise en relation vers une plateforme complète permettant aux vendeurs et prestataires de transformer une opportunité en activité commerciale.**

La marketplace reste le moteur d'acquisition.

Les boutiques restent la vitrine.

Les annonces restent le contenu commercial.

Les messages restent le canal de contact.

Les crédits et boosts restent le moteur de monétisation.

Et **Mon activité** devient la couche qui permet au professionnel de gérer ce qui se passe après la mise en relation.

Le système final doit rester simple :

**Découvrir → Contacter → Vendre → Gérer → Être payé → Recevoir un avis.**

La complexité doit rester dans l'architecture technique, pas dans l'expérience utilisateur.
